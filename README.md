# 运动相机选型平台

一个纯前端平台原型，面向想买运动相机的人回答四件事：**这类相机到底能拍出什么？我该挑哪一台？这台机器强在哪、弱在哪？买回来之后它实际表现如何？**

站点以产品为中心组织，分成三大并列板块，**首页**与**选购笔记**各自独立，**购机指南**内部则是一条可流转的顺序路径：

**首页（能拍什么） | 购机指南（挑一台 → 看这台怎么样 → 看它的实际表现） | 选购笔记（记下我的选购决定）**

首页不是筛选表单，而是一组玩法卡：每张卡讲清一个真实的拍摄场景与具体拍法（隧道穿行的明暗急变、隐形自拍杆的第三人称跟拍、雪面高反光下保住两头细节……），并标出现在哪台机型最拍得动它。看中某个玩法就带着它去挑机器，挑机页会预选这个玩法的场景并在每张卡上标出契合度。玩法网格末尾还有一个「上传我的玩法」入口，用户可以分享自己的拍摄场景与拍法；这类用户内容是本地数据，没有官方证据支撑，UI 上一律带「本地数据」徽标，与编者整理的官方玩法明确区分，也不进入官方玩法库。进入某台机型后，六维能力、官方参数与它最拿手的玩法在一处呈现；再往下一步是它的实际表现：核心数据、社区里的真实抱怨、以及这些抱怨到底出在哪个能力维度上。看中了就记进选购清单，最后在「我的选购」里横向比较并导出 Markdown。

## 数据真实性

**竞品参数、价格、行业动向、技术雷达、人群痛点与玩法支撑证据全部是真实数据**，来自品牌官网、官方新闻稿、专业评测与社区讨论。规则如下：

- 每条外部数据都携带 `SourceRef`：来源类型、发布方、标题、可点击 URL、采集日期。界面上每个字段下方都能点开原文核对。
- **规格与价格**至少有一条 `official` 或 `press-release` 来源。价格标注币种、地区与采集日期，并提示以官网为准。
- **实测类结论**（低光、续航）来自 `review` 类来源并注明媒体，不会写成官方参数。
- **人群痛点**来自 `community` 类来源，保留原贴链接并转述大意，不逐字长段复制用户原文。每条痛点另带 `relatedDimensions`（这条抱怨可能出在哪个能力维度上），该字段是编者判断，界面上标注为「内部分析」，不冒充社区原话。
- **玩法**（`src/data/plays.ts`）的拍法与器材建议是编者撰写的操作指引；每个玩法另带 `evidence`，即证明这个玩法确实有机器支撑的真实产品能力或评测结论，逐条附来源。
- **未发布或传闻内容**（如 Insta360 Ace Pro 3、DJI Osmo Action 7）单独分区并标注未官方确认，不混入在售矩阵。
- **查不到或来源冲突的字段标为「未公开」并说明原因，不猜测、不填近似值。** 例如 DJI Osmo 360 的防水深度、GoPro MISSION 1 系列的裸机重量目前均未公开；Osmo 360 的 8K 帧率在官方新闻稿与渠道页之间存在口径分歧，已在字段说明中记录。
- `src/domain/source-integrity.ts` 提供校验函数，`src/data/data-integrity.test.ts` 遍历全部数据文件作为**自动化闸门**：任何无来源、URL 非法、采集日期越界或未公开却无说明的字段都会让测试失败。

当前数据采集日期为 **2026-08-05**。参数会随厂商更新而过期，页面显著位置标注了采集日期。

界面用徽标区分数据性质，颜色与文字双重编码：

| 徽标                                               | 含义                                                             |
| -------------------------------------------------- | ---------------------------------------------------------------- |
| 官方 / 官方新闻稿 / 专业评测 / 社区讨论 / 零售渠道 | 外部数据的来源类型                                               |
| 内部分析                                           | 编者判断（能力评分、玩法能力依赖、抱怨的维度归因），不是外部事实 |
| 本地数据                                           | 用户在本站内自建的选购记录、使用反馈与上传的玩法                 |

## 产品图片版权

首页玩法卡使用真实的品牌官方营销素材（`src/components/SceneArt.tsx`，10 种场景，图片存于 `public/image/products/`，版权归各品牌所有，登记在 `src/data/image-credits.ts` 的 `IMAGE_CREDITS`）。

竞品卡片与机型详情页的产品图（`src/components/ProductPhoto.tsx`）展示各品牌官网产品页的真实产品图：机型的 `imagePath` 非空时优先渲染该图片，未登记或图片加载失败时自动退回自绘 SVG 形态示意图，任何时刻都不会出现破图或死链。9 款在售机型均已收录官方产品图，存于 `public/images/products/`（注意与场景图目录 `public/image/products/` 不是同一处），登记在 `src/data/image-credits.ts` 的 `PRODUCT_IMAGE_CREDITS`（版权归属与官网来源链接），`data-integrity` 测试会校验每个非空 `imagePath` 都已登记版权。补充或更换图片的流程写在该文件顶部的注释里。图片版权归各品牌所有，仅可用于内部产品分析的识别性展示。

## 阅读体验设计

本站面向的不只是熟悉影像参数的人，因此呈现层遵循三条原则：

**分层露出，不删信息。** 每个页面顶部先给 4 个大字概览（可选机型数、符合当前条件的数量、我记下的机型数、数据采集日等），再进入明细。首页玩法卡主推位给完整步骤，其余卡片只显前两步、剩下的收进折叠区。机型卡片首屏只显最影响决策的几项，完整规格、官方优缺点与全部数据来源都收在折叠区。次要分区（行业动向、未发布机型、我记过的反馈）默认折叠，标题上写清里面有什么、有多少条。

**来源折叠但不削弱。** 列表卡片上不逐字段罗列来源，而是汇总到一个「数据来源（N）」折叠区；单机型详情页仍逐字段挂来源，因为那一页的目的就是逐项核对。**可核对性完全不变**——链接照旧可点开原文，`data-integrity` 自动化闸门一条未动。

**术语改大白话，注解保留。** `src/lib/wording.ts` 集中维护映射：「open-gate」→「全画幅读出」、「Quad Bayer」→「四合一像素」、「动态范围（档）」→「明暗宽容度」、「10bit D-Log M」→「宽容度录制模式」等。大白话标签后带 `ⓘ`，通过 `<abbr>` 的 title 与屏幕阅读器文本给出原术语和计算口径，专业读者不丢信息。分数旁另有定性判读（`describeCapabilityLevel` 输出「偏弱 / 中等 / 较强 / 第一梯队」，`describeSeverityLevel` 把 1–5 的影响程度译成「几乎无感 … 完全没法用」），不看数字也能判断好坏。

**导航始终回答「我能去哪」。** 全站只有一处主导航：顶部悬浮胶囊里的三大并列板块（首页 / 购机指南 / 选购笔记），用 `<ul>` + `aria-current="page"` 表达平级关系，当前板块高亮（`src/components/FlowBar.tsx`）。「购机指南」这一个标签覆盖挑一台、这台怎么样、实际表现三个路由，点它固定回到「挑一台」入口页。三个板块全部是真链接，导航里不留死胡同，也不留空页面。

**购机指南内部仍是顺序流程。** 挑一台 → 这台怎么样 → 实际表现这三步确实有先后关系，因此在这三个路由下会额外出现一条子步骤条（`src/components/GuideSubNav.tsx`），用 `<ol>` + `aria-current="step"` + 序号 + 箭头分隔符表达顺序。它不是第二处主导航——用 `<section aria-label="购机指南进度">` 承载而不是 `<nav>`，全站的可访问性导航 landmark 依然只有一个。依赖机型的两步（这台怎么样、实际表现）没有显式选过机型时落到默认机型（上次看过的那台，或当前推荐第一名，见 `src/domain/default-product.ts`），并在链接上标「默认」、在页面顶部提示可回去重选。

**上下文与导航分工。** 主导航只回答「我能去哪」，当前机型的信息交给内容区顶部一条上下文横条（`src/components/ContextBar.tsx`）：机型名、我把它放在选购流程的哪一档、围绕它记了多少条反馈、一键回到它的详情页。桌面端没有第二套重复链接的侧栏。

**先给出路，再报错。** 空状态与异常都带一个可点的下一步：我的选购为空时引导「去看玩法」或「直接挑机型」，地址里的机型不存在时给「回到挑机型」，筛选无结果时给「重置条件」。

折叠统一用原生 `<details>`/`<summary>`（`src/components/Disclosure.tsx`），天然支持键盘 Enter/Space 与读屏器状态播报，不需要自己维护 `aria-expanded`。

## 三大板块（含购机指南内部三步）

### 首页：能拍什么

站点入口是内容而不是表单。10 个玩法（`src/data/plays.ts`）各自讲清一件事：这个场景拍出来是什么样、具体怎么拍、需要什么器材、主要吃哪些能力。例如「隧道穿行的明暗急变」要求锁定手动曝光并按洞内亮度设定，「磁吸在衣领上的免持第一视角」的真正限制是续航而不是画质，「水下找回被吃掉的红色」靠的是下水前带对滤镜而不是后期。

每张卡带一张自绘场景插画、上手难度标签（开箱就能拍 / 需要一点设置 / 要后期才出效果）、编者标注的能力依赖，以及**现在最拍得动它的机型**与契合度。卡底的折叠区列出这个玩法确有机器支撑的真实证据（附来源）。可按拍摄场景筛选，只看自己会去拍的那一类。

### 购机指南 · 第一步：挑一台

从首页带着玩法进来时，这个玩法的人群会被预选，每张机型卡额外标出「拍这个玩法契合度多少」，让选择和目的对得上；也可以点「不限玩法」回到通用推荐。

选购条件分三层：**拍摄场景**（8 类，可多选）决定各能力维度的权重；**预算**是软条件，超预算的机型不会被藏起来，只按超出比例扣分并明确标注，避免略超预算的更优解被静默过滤；**机身形态**是硬筛选。

匹配度算法在 `src/domain/product-recommendation.ts` 中实现，口径通过界面上的「匹配度怎么算」完整公开。每张卡片给出可读的推荐理由与相对短板，已经记进选购清单的机型会显示当前状态。行业动向与未发布机型各自独立折叠，传闻内容明确标注未获官方确认、不计入推荐。

### 购机指南 · 第二步：这台怎么样

单台机型的完整资料：**六维能力**雷达图（每个维度的分数都能点开官方规格或第三方实测来源）、**官方参数**表（查不到的字段标为「未公开」并说明原因）、以及**它最拿手的玩法**——把 10 个玩法按各自依赖的能力在这台机器上的得分排序，契合度低的也照样列出并点出瓶颈维度，不只讲好的一面。

**强项与短板分开呈现**：逐维度与其余在售机型的均值比较，差距超过 8 分才算（`src/domain/product-context.ts`）。均值不含该机型自身，否则自身的低分会拉低基准、掩盖真实差距。排名第一的机型可能没有任何短板，界面会如实说明而不是硬凑结论。

看中了可以直接记进选购清单：态度（还在看 / 进了候选 / 已排除 / 已入手）、我的预算上限、我打算用它拍哪些玩法、看中什么、还在犹豫什么。机型地址形如 `#/product/insta360-x5`，可直接分享与收藏。

### 购机指南 · 第三步：实际表现

官方参数只说了它能做什么，这一页看的是它实际表现如何：

- **核心数据**：六个能力维度的当前水平，每项都能点开来源核对。
- **社区在讨论什么**：这台机器目标人群的真实抱怨，保留原贴链接，界面上是转述大意、可点开读原文。只显示官方定位人群对应的场景，避免把无关人群的抱怨挂到它头上。
- **问题根因**：把两类反馈（社区讨论 + 我自己录入的）按各自最可能对应的能力维度归拢，再和这台机型在该维度的实际得分并列（`src/domain/feedback-analysis.ts`）。得分偏低且有反馈指向 → 判为「确有短板」；**得分不低却仍有抱怨 → 界面明说这更可能是拍摄方法或场景预期的问题，而不是机器拍不到**。维度归因是编者判断，标注为「内部分析」，不冒充社区原话。
- **记一条我遇到的情况**：录入自己的使用反馈（问题或好评、场景、影响程度、归到哪个维度），保存后立刻并入上方根因分析，并按场景分组回看。

### 选购笔记：我的选购

消费者视角的收尾。记下的机型按选购阶段分组（进了候选 / 还在看 / 已入手 / 已排除），每张卡列出看中点、犹豫点、打算拍的玩法，以及**是否超出你自己设的预算**（标注但不排除，超支与否由你权衡）。

顶部给一个倾向建议，口径刻意保持简单并对用户公开：只在「进了候选」里比较，用你记下的看中点数量减犹豫点数量作为倾向，打平时看六维综合分。犹豫点不少于看中点时它会提醒你先把犹豫的点弄清楚，而不是催着下单；什么理由都没写时它会让你先补几条。**它不替你决定，只是把你已经想清楚的部分摆出来。** 记录可导出为 Markdown，附机型价格、来源声明与本地内容的区分。

## 技术栈与架构

- **React 19 + TypeScript（strict）+ Vite + Tailwind CSS v4**
- **Vitest + @testing-library/react + jsdom**，342 个测试
- 运行时依赖只有 React 本体。不引入状态管理库（`useReducer` + context）、UI 组件库、图表库（手写内联 SVG）、路由库（自建 hash 路由）。依赖版本全部精确锁定。

```text
src/
├─ types/        领域类型与 Result / SourceRef 契约
│                competitor · audience · play · decision · feedback · tech-radar
├─ data/         真实数据集（竞品、玩法、趋势、技术雷达、人群、来源常量）
├─ gateway/      AgentGateway 接口 + 静态实现，UI 只依赖接口
├─ lib/          storage / guards / format / id / download / wording
├─ domain/       纯函数领域逻辑
│                competitor-analysis · product-recommendation · product-context
│                play-matching · feedback-analysis · decision-notes
├─ state/        reducer、Provider、hash 路由、主题、机型记忆、异步资源 hook
├─ components/   外壳与共享组件（FlowBar 主导航三大板块 / GuideSubNav 购机指南内部子步骤
│                / ContextBar / SceneArt 场景插画 / Disclosure / OverviewStats / ThemeToggle / BackToTop / Term）
├─ test/         测试构造器（以真实数据为模板，只覆盖用例关心的字段）
└─ views/        三大板块对应的五个视图
                 HomeView 首页·能拍什么
                 PickerView / ProductView / MonitorView 购机指南内部三步：挑一台 · 这台怎么样 · 实际表现
                 MyDecisionsView 选购笔记·我的选购
```

浏览器里存三份数据，各用独立的 localStorage 键：本地业务数据（`agent-insta:workspace`，带 schema 版本与迁移）、上次看过的机型（`agent-insta:last-product`）、主题选择（`agent-insta:theme`）。后两份是浏览偏好而不是用户录入的业务数据，因此不进 `WorkspaceData`——混进去会让已录入的记录承担不必要的 schema 失效风险。三份都经类型守卫收窄，读失败按「没有记录」处理并回落到默认值。

用户看中的玩法（`activePlay`）只存在内存里，不写入 `WorkspaceData`：它是一次浏览过程中的临时上下文，不该让已有的本地业务数据承担迁移风险。

**持久化结构 v4。** 站点从「需求管理工作台」改为「选购决策与效果跟踪」时（v1/v2 → v3），旧版的洞察、需求、素材与验收记录在新结构中没有对应字段——无法把「一条需求」翻译成「一条选购记录」而不凭空编造用户意图，因此 `migrateWorkspaceData()` 明确以空记录起步，而不是猜一个映射。v3 → v4 新增用户自己上传的玩法（`userPlays`），是纯增量字段，不影响 decisions/feedback，因此这一步只补一个空数组，不清空任何已有记录。迁移在类型守卫之前运行，`readJson` 返回迁移后的值。

路由是自建 hash 路由，`product` 与 `monitor` 各带一个机型段（`#/monitor/dji-osmo-action-6`）。机型 id 只允许小写字母、数字与连字符，非法或未知地址返回 `null` 交由上层提示，而不是静默回落；带机型段的路由缺了机型段时回到选型对比页而不是报错。

领域逻辑全部是纯函数并单独测试。所有可能失败的操作返回 `Result<T>` 而不抛异常，错误都带上面向用户的原因与下一步建议。

`AgentGateway` 是明确的数据接口边界：视图层不直接 import 数据文件。未来要接真实检索或模型服务，只需换一个 `AgentGateway` 实现，UI 不动。浏览器内不存放任何密钥，运行时不向第三方站点发起请求。

## 无障碍

- 浅色与深色两套主题的正文与强调色对比度均达 WCAG AA（4.5:1），可交互边界达 3:1；来源徽标不单靠颜色区分，都带文字标签。主题默认跟随 `prefers-color-scheme`，用户显式切换后记住选择。
- 语义结构完整：`header` / `nav`（`aria-current="page"`）/ `main` / `footer`，标题层级正确，表格带 `caption` 与 `th scope`，表单控件全部关联 `<label>`。
- 提供「跳到主内容」键盘链接；视图切换后焦点移到主区域；Modal 支持 Esc 关闭并在关闭后把焦点还给触发元素。
- SVG 图表都提供可展开的数据表作为无障碍替代内容；场景图片带说明性 `aria-label`。
- 折叠区用原生 `<details>`/`<summary>`，键盘 Enter/Space 即可展开，读屏器会播报展开状态。
- 顶部主导航用 `<ul>` + `aria-current="page"` 表达首页 / 购机指南 / 选购笔记三大板块的并列关系，三项都是可达的真链接；购机指南内部的三个子步骤另有一条 `<ol>` + `aria-current="step"` 子步骤条（`section aria-label="购机指南进度"`），不构成第二处 `nav` landmark。
- 术语注解用 `<abbr>` 承载，屏幕阅读器能读到完整的技术口径说明。
- 操作反馈通过 `aria-live="polite"` 区域播报。
- 响应式：单列居中容器（`max-w-6xl`），头部导航在窄屏可横向滚动、站点标题退为 `sr-only`，玩法与机型卡片网格逐级降列。
- 尊重 `prefers-reduced-motion`。

> 完整的 WCAG 合规验证需要辅助技术实测与无障碍专家评审，本项目只保证上述可自动化与可自查的部分。

## 部署

### Vercel（推荐）

仓库已含 `vercel.json`（framework 为 vite，构建命令 `npm run build`，产物目录 `dist`）。

```bash
npm i -g vercel
vercel          # 首次部署，按提示关联项目
vercel --prod   # 部署到生产环境
```

或在 Vercel 控制台 **Add New → Project** 导入 Git 仓库，框架会被自动识别为 Vite，无需额外配置。路由使用 hash（`#/product/insta360-x5`），因此不需要服务端 rewrite。

### GitHub Pages

由于用的是 hash 路由，静态托管同样可用。需要把 `vite.config.ts` 里的 `base` 从 `'/'` 改为 `'/<仓库名>/'`，然后把 `dist/` 发布到 `gh-pages` 分支。
